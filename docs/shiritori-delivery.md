# しりとり辞書の分割配信

CSVは編集用の原本として残す。ゲームの起動時は `data/shiritori-delivery/index.json` の読み・最低レベル・分割先・集計だけを取得する。説明・表記・画像・意味ごとのレベル・ジャンルは分割JSONで必要時だけ取得する。ゲームは `whitelist.csv` と大きな `shiritori-grade-policy.js` をダウンロードしない。

## 取得の範囲

- 入力の登録確認と手書き候補の辞書照合は軽量な読み索引を使う。全件の説明や画像参照は保持しない。
- 入力した語の意味は、その語を含む最大128読みのファイルだけ取得する。同音異義語は分割しない。
- CPUとヒントは、今の頭文字で、選択レベル・ジャンルに候補が存在するファイルだけ取得する。候補の各意味にも従来のレベル・ジャンル条件を適用する。
- CPUの先手は候補が存在する頭文字から選ぶ。ヒントの初手は候補がある最初の頭文字を使う。
- 設定の候補数は意味を全取得せず索引の集計から計算する。同じ読みを重複カウントしない。
- 分割ファイル名は内容のSHA-256を含む。同じファイルの重複取得をまとめ、ブラウザのHTTPキャッシュを使う。メモリ内の分割ファイルは直近12個と現在の候補集合に限定する。大きなCSVをlocalStorageに入れない。
- 通信失敗で登録語を未登録扱いしたり、CPUを負けにしたりしない。「もういちど よみこむ」で同じ手番を再試行できる。リセット後に古い手番を確定しない。

## 語彙や分類を更新するとき

1. 従来どおりCSVと意味別の難易度決定を更新する。
2. `python scripts/build-shiritori-grade-bands.py` を実行する。難易度表に続いて分割配信データも自動生成する。原本のハッシュと難易度表が合わない場合は生成を停止する。
3. `node scripts/build-shiritori-delivery.cjs --check` と `node tests/shiritori-delivery.cjs` を実行する。
4. 更新した `data/shiritori-delivery/index.json` と生成した `chunks/*.json` を原本・難易度表と一緒に公開する。

分類ロジックだけを変えた場合は `node scripts/build-shiritori-delivery.cjs` で再生成する。ビルダーは既存のCSVパーサー・難易度表・ジャンル分類を使い、別の分類規則を持たない。古いハッシュ名のファイルは、更新前の画面からの取得を壊さないよう自動削除しない。

## 検証

`node tests/shiritori-delivery.cjs` は全読み・全意味・画像対応、5レベルとジャンル選択の集計95条件、同時取得の共有、失敗後の再試行、キャッシュ上限、生成ファイルの一致を確認する。

`node tests/shiritori-delivery-browser.cjs` はPlaywrightを使い、デスクトップ・スマホで起動時の実取得量、必要な意味の取得、対戦、プレイヤーとCPUの通信失敗・実際の再試行ボタン、リセットとの競合を確認する。環境に応じて `PLAYWRIGHT_MODULE` にPlaywrightのパスを指定する。

2026-10-28の21,583意味・20,957読みでは200ファイル、最大59,824バイト。既定のヒントOFFでの初期辞書取得量は669,569バイト。旧CSVと難易度表の合計5,940,323バイトから約89%減少した。これは辞書関連の非圧縮サイズの比較であり、手書き認識モデル等を含むページ全体の通信量ではない。

読み索引は引き続き全読みを含むため、語数に比例して増える。今回は実測済みの約2万語が対象で、将来の9万5千件での端末性能は未計測。索引自体が問題になる規模では索引も分割するか、サーバー検索を検討する。オフラインでは未取得の意味・候補を新規取得できず、再接続後に再試行する。

## 日本の地名・駅名の任意追加辞書

95,520意味・85,326読みを別パックで登録した。通常起動では取得せず、設定でONにしたときだけ追加索引を取得する。通常CSVへの追記は行わない。CPUジャンル、同音異義語、候補検索、版の整合性は両辞書を統合して扱う。[登録・出典・更新手順](shiritori-japan-places.md)。
